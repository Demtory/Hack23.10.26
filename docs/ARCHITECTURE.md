# Архитектура приложения

Документ описывает реализованный прототип после002. Прежнее предложение
с SQLAlchemy/Tailwind/TanStack/Recharts/SourceAdapter не соответствовало коду;
эти зависимости и классы не используются и не устанавливались.

## Стек и модули

- Python3.12, FastAPI, Pydantic2; SQLite через стандартный sqlite3, WAL.
- React18, TypeScript, Vite; существующие CSS и компоненты, fetch/useState/useEffect.
- Один Dockerfile собирает фронтенд и раздаёт его через FastAPI на8000.
- `main.py`: приложение, startup, статика, безопасные422 и OpenAPI.
- `config.py`: Config из окружения; `db.py`: схема/connect/транзакции.
- `schemas.py`: входные/выходные DTO; `security.py`: пароли/серверные сессии; `oidc.py`: OIDC-клиент.
- `seed.py`: import/export снимка, settings, подготовка upgrade.
- `scoring.py`: существующие формулы, defaults, metadata и FEATURE_GENERATIONS.
- `store.py`: recompute, сохранение/чтение score_runs/customer_scores.
- `api.py`: роуты, валидация настроек, фильтры/сортировки, SSE и текст Prometheus.
- `frontend/src/api.ts`, `types.ts`, `App.tsx`, `pages/`: запросы, состояние и экраны.

Источник: seed при первом старте либо PUT `/api/v1/source/snapshot`.
Pydantic проверяет полный снимок → транзакция заменяет данные → scoring считает
услуги/клиентов/деньги → store проверяет и сохраняет кэш → commit.
SSE и резервный опрос замечают новый run; серверный фоновый scheduler отсутствует.
`recomputeIntervalSec` не означает реализованный периодический пересчёт.

## Данные и единицы

Имена таблиц/колонок заданы в `db.py:SCHEMA`:
accounts(balance,withdraw_balance,total_replenished,bonus_balance), services(price),
transactions(amount) содержат целые евроценты. JSON использует camelCase;
source API сохраняет евроценты точно, UI/detail/summary выводят EUR.
Strict money input0…2^63−1; дробная/экспоненциальная запись, string/bool/null
отклоняются. Производный overflow отклоняет операцию целиком.

settings(id,payload,version,updated_at,feature_schema_version) хранит конфигурацию.
score_runs(id,as_of,created_at,settings_version,summary) и customer_scores — кэш
одного расчёта; старые runs ограничены20. Пользовательская version и внутреннее
поколение признаков имеют разный смысл. Схема старой settings дополняется одной
колонкой DEFAULT1 через PRAGMA/ALTER без пересоздания таблиц.

## Согласованное чтение и API

Пути и прежние поля сохранены; актуальный контракт — `openapi.json`, экспортируемый
`scripts/export_openapi.py`, и `/api/v1/openapi.json`. Runtime и сохранённая схема
сравниваются тестом. FastAPI округляет schema bounds в float; генератор приложения
восстанавливает точную int64-границу денежных полей. JSON Schema не различает
100 и100.0; строгую запись дополнительно проверяет runtime.

GET customers сначала восстанавливает недостающий кэш, затем в явной read-транзакции
читает latest run, JOIN accounts, count, страницу, topLosses и глобальную summary.
Контекст calculation(runId,settingsVersion,thresholds) относится ко всему ответу.
Пороги копируются в summary при расчёте, а не читаются отдельно из current settings.
TopLosses: до5 клиентов по expected_loss DESC/id ASC во всей выбранной совокупности;
q ищет email по LIKE, а числовой запрос — ещё и точный ID; level фильтрует классификацию. Страница
и сортировка таблицы на top не влияют. Верхняя сводка и /metrics глобальные.
Фронтенд публикует единый bundle одним setState и игнорирует устаревшие ответы.

## Сессии

Сервер хранит хеш токена и срок в sessions. Защищённые операции принимают sid
cookie или Bearer. Непустая cookie имеет приоритет даже при ошибке/истечении;
нет переключения на другую Bearer-сессию. Без действительной сессии401.
Logout без require_user отзывает только выбранный токен и очищает cookie;
повторный/анонимный выход200. Клиент очищает токен/user после успешного ответа,
при отказе сохраняет экран и предлагает повтор. Независимые сессии не затрагиваются.
Метрики /metrics и /api/v1/metrics сохраняют прежнюю публичность.

## Прогноз оттока

`GET /api/v1/analytics/forecast?pastDays=30&horizonDays=30` считает два ряда по
сохранённым деталям последнего расчёта. Факт — услуги с `expiresAt` не позже среза,
которые ещё не удалены (значит, не продлены). Прогноз — услуги с истечением в окне
впереди: ожидаемое число непродлений — сумма P(score), ожидаемые потери — сумма
P(score)×price×(1−mitigation) по дням. Дат удаления в данных нет, поэтому исторический
ряд не строится; в ответе есть `note`, который интерфейс показывает рядом с графиком.
Окна ограничены 90 днями, ответ детерминирован при фиксированном `AS_OF`.

## OIDC

OIDC включается переменными `OIDC_ISSUER` и `OIDC_CLIENT_ID`; без них маршруты
`/auth/oidc/start` и `/callback` отвечают404, а экран входа показывает только пароль.
Поток — Authorization Code + PKCE(S256): `state`, `nonce` и `code_verifier` лежат
в `oidc_flows`, запись одноразовая и живёт10минут. ID token проверяется по JWKS(RS256):
подпись, `iss`, `aud`/`azp`, `exp`/`iat`/`nbf` с допуском30с, `nonce`, `sub`, email.
Первый вход создаёт пользователя по email с пустым `password_hash`; такой пользователь
не может войти по паролю, а прежние парольные аккаунты не меняются. Любая ошибка
возвращает303 на `/#/login?sso_error=<код>` без сессии. `OIDC_INTERNAL_BASE` задаёт
внутренний адрес issuer для запросов из контейнера, пока браузер видит публичный.
Кэш discovery/JWKS —5минут, новых зависимостей нет.

## Добавление признаков

Инструкция — README и MODEL, раздел10. Новое поколение объявляется последовательно
в FEATURE_GENERATIONS вместе с defaults/metadata/вычислением фактора. Старые
валидные настройки дополняются только новыми отсутствующими кодами с0, явные
значения сохраняются. Upgrade, version+1, время и один recompute фиксируются
одной startup-транзакцией; несколько переходов повышают version один раз.
Повторный restart не повышает version. Неизвестное поколение/код, потерянный старый
ключ и некорректные значения приводят к отказу, без молчаливого ремонта.
Новых реальных признаков и формул в002 не добавлено.

## Атомарное изменение модели и снимка (001-model-reliability)

PATCH настроек и PUT снимка имеют одного владельца SQLite-транзакции:
BEGIN IMMEDIATE → чтение текущей версии → проверка → запись → пересчёт/кэш →
проверка конечности, представимости SQL-значений и JSON/контракта → commit.
Сборка JSONResponse происходит до фиксации. Вспомогательные save_settings,
replace_snapshot и recompute не фиксируют транзакции самостоятельно.
При ошибке, включая отказ commit до успешной фиксации, выполняется rollback;
неожиданный внутренний сбой возвращает безопасный500, входная ошибка —422.
Доставка ответа, оборвавшаяся после успешного commit, не означает откат.

При startup init_db и bootstrap auth предшествуют транзакции данных;
defaults/seed/recompute фиксируются вместе. Восстановление отсутствующего кэша
также явно владеет транзакцией. После намеренной очистки наличие успешного
score_run отличает принятую пустую БД от новой, поэтому seed не возвращается.
AUTOINCREMENT не сбрасывается. Совместимые старые данные и настройки сохраняются.

Новые объяснения хранятся в существующем detail JSON; SQL-миграций нет.
Все detail проверяются до публикации; старый JSON без explanationRules читается
с пустым массивом. Полный response DTO сохраняет прежние поля и единицы.
Существующий SSE замечает только зафиксированный новый run через отдельное
соединение; rollback не создаёт успешного события. SSE и polling сохранены.
Обработчик ошибок валидации не возвращает сырой input/ctx, чтобы NaN/Inf внутри
ошибки не приводили к сбою JSON и не раскрывали содержимое снимка.
