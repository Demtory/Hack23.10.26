# Модель риска оттока — v1

> Версия после профилирования реального датасета. Отличия от v0:
> camelCase-поля, `bonusState` — строка, транзакции привязаны к услуге,
> денежная оценка считается от ближайшего платежа с ограниченным влиянием
> баланса, добавлена защита от устаревших статусов.

---

## 1. Принципы

1. **Без ML.** В данных нет истории и меток «уйдёт / не уйдёт» — обучать
   supervised-модель не на чем. Делаем объяснимый score с настраиваемыми весами.
2. **Один score — три ответа.** Score — «кому», драйверы — «почему»,
   денежная формула — «сколько».
3. **Всё считается из данных.** Никаких захардкоженных ID и сумм.
4. **Неизвестность — состояние.** Если данных мало — `score=null` и «Нет оценки»,
   а не `0`.
5. **Данные могут быть устаревшими.** Статус `active` с истёкшим `expiresAt` —
   это не «всё хорошо», а сигнал, что статус не обновили. Модель это ловит.
6. **Баланс не обнуляет потери.** Он покрывает ближайший платёж, но не
   удерживает клиента. Влияние баланса ограничено коэффициентом.

## 2. Данные: фактические поля

Источник — `data/raw/data.json` (PostgreSQL-совместимая схема в
`data/raw/001_schema.up.sql`). Поля в JSON — **camelCase**, деньги — целые
**евроценты**.

### accounts

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int | PK |
| `email` | str | уникальный |
| `balance` | int | основной баланс, центы |
| `withdrawBalance` | int | реферальный, можно вывести/перевести на баланс |
| `totalReplenished` | int | всего реальных пополнений, центы |
| `bonusBalance` | int | бонусы, центы |
| `bonusState` | `locked` / `unlocked` | **строка, не boolean**; бонусы тратятся только при `unlocked` |

### services

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int | PK |
| `name` | str | `^[A-Za-z0-9-]+$` |
| `ownerId` | int | → `accounts.id` |
| `paymentTerm` | enum | `hour`, `week`, `month`, `quarter_year`, `half_year`, `year` |
| `autoProlong` | bool | автопродление |
| `createdAt` | ISO UTC | |
| `expiresAt` | ISO UTC | `>= createdAt` |
| `status` | enum | `active`, `blocked`, `deleted`, `suspended`, `prolong_wait` |
| `price` | int | стоимость **за период**, центы |

### transactions

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | int | PK |
| `amount` | int | 0…1000 центов; **не равен `price`** и не используется как выручка |
| `status` | `performed` / `not_performed` | |
| `performedAt` | ISO UTC / null | null только для `not_performed` |
| `createdAt` | ISO UTC | |
| `type` | `prolong` / `order` | |
| `serviceId` | int | → `services.id`; аккаунт получаем через `services.ownerId` |

**Важно:** `amount` генерируется независимо от `price` (см. README датасета).
Для денежной оценки используем `price`, а `amount` — только как сигнал
неоплаченного счёта.

**Доступные деньги:**

```
available = balance
          + (bonusState == "unlocked" ? bonusBalance : 0)
          + (include_withdraw_balance ? withdrawBalance : 0)
```

`include_withdraw_balance` — настройка, по умолчанию `true`.

## 3. Признаки

Каждый признак нормирован в `[0, 1]`, `1` — максимальный риск.
Веса задаются в относительных единицах; при расчёте нормируются.

| Код | Уровень | Что измеряет | Формула (0…1) | Вес |
|---|---|---|---|---|
| `expiry_pressure` | услуга | Сколько осталось до конца периода | `<0` → 1.0; `0–3` дн → 1.0; `4–7` → 0.75; `8–14` → 0.5; `15–30` → 0.25; `>30` → 0.05. Если `autoProlong=true` **и** `available >= price`, умножить на 0.4 | 0.40 |
| `funds_gap` | аккаунт × услуга | Хватает ли на ближайшее продление | `available < price` → 1.0; иначе `max(0, 0.3 × (1 − available / (3 × price)))` | 0.25 |
| `autorenew_off` | услуга | Клиент отключил автопродление | `1`, если `autoProlong=false`, иначе 0 | 0.10 |
| `status_pressure` | услуга | Состояние услуги | `prolong_wait` → 1.0; `blocked` → 0.9; `suspended` → 0.7; `active` → 0.0 | 0.10 |
| `payment_history` | аккаунт | Были ли неоплаченные счета | Неоплаченный `prolong` → 1.0; неоплаченный `order` → 0.6; иначе 0.0; нет транзакций → `null` | 0.10 |
| `commitment` | аккаунт | Насколько клиент «вложился» | `1 − min(1, totalReplenished / (3 × Σ price аккаунта))` | 0.05 |
| `auto_off_share` | аккаунт | Привычка отключать автопродление | доля неудалённых услуг аккаунта с `autoProlong=false` | 0.00 (поколение 2) |

### 3.1. Устаревшие статусы

В предоставленном наборе есть расхождения: `active` с `expiresAt` в прошлом,
`prolong_wait` старше 5 дней. Это не повод молча считать их «нормальными».

Правила:

- `status ∈ {active, suspended}` и `expiresAt < now` → `status_pressure = 1.0`,
  флаг `stale_status = true`, причина «срок истёк, статус не обновлён».
- `status == prolong_wait` и просрочка > 5 дней → тот же флаг, причина
  «просрочена более 5 дней, должна быть deleted».
- `status == deleted` → услуга не оценивается (это уже потеря).
- `status == blocked` → оценивается, но с минимальным score 60: клиент ещё
  в базе, но пользоваться не может.

### 3.2. Минимальные score по статусу

| Статус | Минимум | Почему |
|---|---:|---|
| `prolong_wait` | 70 | Идёт 5-дневное окно, дальше `deleted` |
| `blocked` | 60 | Услуга недоступна, нужен win-back |
| устаревший `active`/`suspended` | 70 | Данные противоречат статусу, нужен разбор |

Минимум применяется после взвешенной суммы: `score = max(score, floor)`.

## 4. Score услуги

```
f_i = value_i, если признак доступен, иначе 0.5 (нейтрально)
score_service = 100 × Σ(w_i × f_i) / Σw_i
```

Веса нормируются при расчёте, поэтому их сумма может быть любой `> 0`:
увеличение одного веса перераспределяет вклад, а не раздувает score.
Нейтральное значение 0.5 —
это «неизвестно», не «хорошо» и не «плохо». Пропуск данных не должен
искусственно занижать или завышать оценку.

Считаем `confidence` — долю доступного веса. Если `confidence < 0.5` или
услуга `deleted` — не оцениваем. Если у клиента нет ни одной оцениваемой
услуги — `score=null`.

---

## 5. Score клиента

```
score_customer = min(100, max(score_service) + 4 × max(0, N_at_risk − 1))
```

- `N_at_risk` — число услуг со score ≥ 40; если их 0 или 1, добавки нет.
- Худшая услуга задаёт срочность, дополнительные услуги под риском увеличивают
  цену ошибки.
- `deleted` не входит.
- Если все услуги `deleted` — `score=null`, причина «Все услуги удалены»,
  а не «нет данных». Это разные состояния.

**Уровни:**

| Уровень | Условие | Действие |
|---|---|---|
| Высокий | `≥ 70` | Звонить сегодня |
| Средний | `40…69` | В программу удержания |
| Низкий | `< 40` | Наблюдать |
| Нет оценки | `null` | Разобраться в данных |

Пороги — настройка, не константы.

## 6. Вероятность оттока

Для денежной оценки score **услуги** переводится в вероятность:

```
P(churn) = 1 / (1 + exp(−(score − 65) / 12))
```

| Score | 30 | 40 | 50 | 60 | 70 | 80 | 90 |
|---|---|---|---|---|---|---|---|
| P | 0.05 | 0.11 | 0.22 | 0.40 | 0.60 | 0.78 | 0.89 |

Ограничение `P ∈ [0.02, 0.95]`. Это бизнес-допущение; при появлении истории
кривую можно откалибровать без изменения остальной системы.

## 7. Деньги

### 7.1. Что считаем

Ближайший платёж по услуге — это `price` за её период. Не пересчитываем всё
в месяц: в синтетическом наборе почасовые цены дают нереалистичный MRR
(€9/час × 730 = €6 570/мес), и такой показатель затмил бы всё остальное.
Для бизнеса понятнее: **«сколько недополучим при ближайшем продлении»**.

Если понадобится месячный run-rate, его можно добавить отдельной колонкой
(`price × множитель периода`), но headline — ближайший платёж.

### 7.2. Покрытие балансом

```
coverage = min(1, available / Σ price оцениваемых услуг)
```

Баланс распределяется на все оцениваемые услуги пропорционально цене,
поэтому одни и те же деньги не считаются дважды.

### 7.3. Влияние баланса

```
balance_mitigation = 0.5   # настройка
mitigation = balance_mitigation × coverage
expected_loss = Σ( P(score_услуги) × price_услуги × (1 − mitigation) )
amount_at_risk = Σ price_услуг со score ≥ 40
covered_loss  = Σ( P × price × mitigation )
```

Почему не вычитаем баланс целиком: он закрывает **ближайший** платёж, но
клиент всё равно уходит, и будущая выручка теряется. Считаем, что баланс
снижает потерю не более чем на 50% (`balance_mitigation = 0.5`). Это
защищает от нулевой оценки в данных, где баланс покрывает все цены.

### 7.4. Пример

Клиент: `balance = €4.00`, бонусов нет, `totalReplenished = €120`.
Услуга: `€9.90 / month`, `autoProlong = false`, `active`, истекает через 2 дня,
неоплаченных счетов нет.

| Признак | Значение | Вес | Вклад |
|---|---|---|---|
| `expiry_pressure` | 1.0 | 0.40 | 0.400 |
| `funds_gap` | 1.0 (€4 < €9.90) | 0.25 | 0.250 |
| `autorenew_off` | 1.0 | 0.10 | 0.100 |
| `status_pressure` | 0.0 | 0.10 | 0.000 |
| `payment_history` | 0.0 | 0.10 | 0.000 |
| `commitment` | 0.0 | 0.05 | 0.000 |
| **Итого** | | | **0.750 → score 75 (высокий)** |

`P = 1 / (1 + exp(−(75 − 65)/12)) ≈ 0.697`

`coverage = 4 / 9.9 ≈ 0.404` → `mitigation = 0.5 × 0.404 ≈ 0.202`

`expected_loss = 0.697 × 9.90 × (1 − 0.202) ≈ €5.51`

`amount_at_risk = €9.90`, `covered_loss ≈ €1.39`.

### 7.5. Что показываем в UI

- **Ожидаемые потери при ближайшем продлении** — headline.
- **Сумма платежей под риском** — `amount_at_risk`.
- **Покрытие балансами** — `coverage` в % и €.
- Тултип: «Баланс снижает немедленную потерю, но не отменяет уход клиента».

```json
  "thresholds": {"medium": 40, "high": 70},
  "probability": {"midpoint": 65, "steepness": 12, "floor": 0.02, "ceiling": 0.95},
  "money": {"balance_mitigation": 0.5, "include_withdraw_balance": true},

  "version": 1

```

Валидация: конечные веса `≥ 0`, сумма `> 0`; `0 < medium < high < 100`;
`0 ≤ balance_mitigation ≤ 1`; `steepness > 0`.

### 9.1. Поколения и пресеты

- Новый признак объявляется новым поколением `FEATURE_GENERATIONS`; при старте
  старые настройки дополняются его кодом с весом 0, прежние оценки не меняются.
  Так добавлен `auto_off_share` (поколение 2): при весе 0 клиент 6 остаётся 89.0.
- Готовые наборы весов («Сбалансированный», «Деньги важнее», «Срочность важнее»,
  «Статус и оплата») заданы в `backend/app/presets.py`; свои наборы лежат в таблице
  `weight_presets` и отдаются `/api/v1/model/presets`.
- Пресет меняет только веса. Пороги, минимумы по статусам и денежные правила
  остаются отдельными настройками.

## 10. Как добавить признак

Признаки живут в `backend/app/scoring.py`: значение/подпись в `_score_service.values`,
metadata в `FEATURES_META`, рекомендованный вес в `DEFAULT_SETTINGS.weights`.
Для добавленного кода обязательно объявить следующее последовательное поколение:

```python
# Пример будущего изменения; в002 реальный новый фактор не добавлен.
FEATURE_GENERATIONS = {
    1: frozenset({"expiry_pressure", "funds_gap", "autorenew_off",
                  "status_pressure", "payment_history", "commitment"}),
    2: frozenset({"usage_pause"}),
}
```

Исходное поколение1 фиксировано. Старая валидная конфигурация получает новый
отсутствующий вес0; прежние веса, пороги, деньги и явно заданный новый вес
сохраняются. Новая база получает рекомендованные значения текущего поколения.
Внутренняя `settings.feature_schema_version` отличается от пользовательской version.
Переход нескольких поколений повышает version один раз; повторный restart её не меняет.
Payload, поколение, version, время и результаты публикуются одной startup-транзакцией.
При отказе остаётся прежнее состояние. Пропавший старый ключ, неизвестный код/поколение,
NaN и отрицательный вес не исправляются автоматически. Проверять временную старую
базу, новый0/явный вес, повторный запуск и отказы по `test_settings_upgrade.py`.
Фронтенд получает metadata и имеет fallback для ещё неизвестного ему описания.


## 11. Проверка на реальном наборе

Что уже видно в `data/raw/data.json`:

- 10 аккаунтов, 30 услуг, 100 транзакций; по 3 услуги на аккаунт.
- У каждого аккаунта все три услуги одного статуса (артефакт генератора):
  2 аккаунта полностью `deleted`, 2 — `prolong_wait`, 2 — `blocked`,
  2 — `active`, 2 — `suspended`.
- `active` услуга с `expiresAt` 4 дня назад; `prolong_wait` — от 39 до 404 дней
  просрочки. Модель помечает это `stale_status`.
- Баланс + бонусы + withdraw покрывают сумму цен у всех 10 аккаунтов
  (`coverage = 1.0`). Поэтому формула «вычесть баланс» дала бы нулевые потери —
  отсюда ограничение `balance_mitigation = 0.5`.
- `amount` транзакций не связан с `price`; для денег используем `price`.
- 33 из 100 транзакций — `not_performed`; у 10 услуг есть неоплаченные счёта.

Санити-проверки:

1. Просроченная `active` и `prolong_wait` попадают в высокий риск.
2. Здоровая `active` с запасом баланса и автопродлением — низкий.
3. `deleted` не попадает в риск, но виден как «все услуги удалены».
4. Сортировка по деньгам не обязана совпадать с сортировкой по score:
   дешёвая, но очень рискованная услуга может дать меньшую сумму.

## 12. Ограничения

- Модель экспертная, не обученная: нет меток и истории.
- `deleted`/`blocked` — уже потерянные или недоступные; не считаем их
  «риском оттока», но blocked оцениваем для win-back.
- `amount` не используем как выручку — только как сигнал неоплаты.
- `totalReplenished` — прокси лояльности, не срок жизни; при появлении
  `createdAt` у аккаунта добавим tenure.
- Дата `as_of` должна быть фиксирована для демо, иначе статусы «поплывут».
- Суммы — евроценты; валюта отображения уточняется.


## Надёжность расчёта и объяснения (001-model-reliability)

Все числовые настройки конечны. Midpoint может быть любым конечным значением,
включая10000: сигмоида вычисляется устойчиво с прежними floor/ceiling.
При переполнении суммы конечных весов используется эквивалентное нормирование
через максимум; на обычных данных арифметика и денежное округление сохранены.
Контрольный пример по-прежнему даёт score75 и потери551цент.

Взвешенные причины `drivers` сохраняют прежний смысл. Дополнительные
`explanationRules` показывают применённые status/stale минимумы у услуги,
а бонус за несколько услуг и ограничение100 — у клиента. Изменения разных
услуг нельзя складывать как клиентскую прибавку. При99→107→100 реальная
прибавка клиента1: бонус+8 и cap−7 показаны отдельно.

Переходы объяснений округляются до одной десятичной позиции; delta считается
из округлённых beforeScore/afterScore. Реальный минимум69.96→70 показывает
70.0→70.0, delta0.0 с пояснением, что после округления оценка не изменилась.
Минимум без реального эффекта не создаёт дополнительную причину. Это не меняет
сам расчёт. Полный контракт: `specs/001-model-reliability/contracts/api.md`.

При отсутствии транзакций payment_history остаётся неизвестным. Если остальных
взвешенных признаков достаточно, клиент всё ещё оценивается; иначе — unknown.
Обязательные финансовые значения и autoProlong не подставляются из defaults:
неполный исходный снимок отклоняется полностью. Явные нули/false допустимы.
Исторические нули нельзя автоматически признать достоверными или восстановить
их происхождение. Вероятность и денежные потери остаются экспертными эвристиками,
не статистически подтверждённым прогнозом.

## Уточнения002 без изменения формул

Доля веса — weight/sum(weights); вклад в базу услуги —100×доля×значение.
Неизвестный фактор заменяется на0.5, полнота определяет возможность оценки.
Нулевой вес не отключает status/stale minima. Клиент: max оценённых услуг,
