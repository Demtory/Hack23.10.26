# Ответы на вопросы жюри

Короткие ответы по 20–40 секунд. Если не знаете — так и скажите: «не проверяли,
вот как бы проверили». Это ценится выше выдумки.

## 1. Почему не машинное обучение?

В данных только текущие статусы: нет меток «ушёл / остался» и истории изменений.
Обучать не на чем — 10 записей дадут подгонку, а не модель. Поэтому прозрачные правила
с редактируемыми весами, и это осознанное решение, а не упрощение. Как только появятся
исходы, шкала калибруется на них без смены архитектуры.

## 2. Откуда берётся вероятность P(score) — это калибровка?

Нет. Это логистическое преобразование шкалы 0–100 с параметрами midpoint/steepness,
настроенное вручную. Мы нигде не называем его статистически подтверждённой
вероятностью: в интерфейсе и API написано «экспертная оценка». Нужна честная
калибровка — понадобятся фактические непродления за период.

## 3. Как считается денежная оценка?

Берём ближайший платёж по каждой услуге (`price`), умножаем на вероятность
непродления: `Σ P(score) × price × (1 − 0,5 × покрытие)`. Баланс гасит потерю не более
чем наполовину: деньги отложены, но клиент всё равно может уйти. `amount` транзакции
не используем — он не равен цене продления.

## 4. Почему такие признаки и веса?

Шесть признаков из условий кейса: срок, нехватка денег, автопродление, статус,
история неоплат, лояльность. Седьмой — «доля услуг без автопродления» — добавили
как пример расширяемости: он включается весом, по умолчанию 0, поэтому старые
оценки не меняются. Веса — экспертная стартовая гипотеза (0,40 / 0,25 / 0,10 /
0,10 / 0,10 / 0,05). Любой вес меняется в панели, пересчёт мгновенный, поэтому команда
может подстроить модель под реальные приоритеты без релиза.

## 5. А 10 000 клиентов потянет?

Да, замеряли: загрузка снимка с пересчётом — 3,1 с, список p95 24 мс, глубокая
страница p95 37 мс, карточка 1,4 мс, `/metrics` 0,9 мс, прогноз после кэша 1,3 мс.
Сортировка и пагинация — в SQL по кэшу `customer_scores`, поэтому от размера выборки
не зависят. Методика — `docs/LOAD_TEST.md`.

## 6. Почему SQLite, а не Postgres?

Один контейнер, ноль внешних сервисов, данные на volume — жюри запускает одной
командой. Для 10k клиентов хватает с запасом. При росте меняется `DATABASE_URL`:
доступ через SQLAlchemy, схема переносится почти без изменений. Узкое место при росте —
пересчёт на запись, тогда нужен инкрементальный расчёт.

## 7. Что с безопасностью?

Пароли — PBKDF2-SHA256 с солью, сессии хранятся в БД хешем, cookie HttpOnly + SameSite=Lax.
Без сессии API отдаёт 401, включая `/metrics`? — нет, `/metrics` публичный по условиям
кейса, но там только агрегаты. OIDC: Authorization Code + PKCE, state и nonce одноразовые,
подпись RS256 по JWKS, проверка iss/aud/exp/nonce. Секреты только в `.env`, в репозиторий
не попадают.

## 8. Как добавить новый признак?

Три шага: значение и подпись в `_score_service`, метаданные в `FEATURES_META` и вес
в `DEFAULT_SETTINGS`, затем объявить новое поколение в `FEATURE_GENERATIONS`. UI сам
нарисует ползунок, старые настройки дополнятся весом 0 без сброса. Рецепт — в README.

## 9. Что будет, если данные изменятся во время работы?

Пересчёт идёт одной транзакцией: настройки, снимок и результаты фиксируются вместе.
Ошибка валидации или расчёта откатывает всё — полу-состояния не бывает, после отказа
приложение продолжает работать. Клиенты узнают об обновлении по SSE, есть резервный
опрос раз в 15 секунд.

## 10. Где хранятся данные и что с персональными?

Всё локально: SQLite в Docker-томе, наружу уходят только агрегаты в `/metrics`.
Email — единственное персональное поле, оно нужно для рейтинга и письма клиенту.
Внешних сервисов в базовом режиме нет; при SSO добавляется провайдер входа.

## 11. Чем вы лучше «просто дашборда»?

Дашборд показывает отчёт. Мы доводим до действия: у каждого клиента есть причина
одной фразой, деньги и готовое письмо под ситуацию. Плюс всё объяснимо и настраивается:
маркетолог меняет вес и сразу видит, как меняется приоритет.

## 12. Что не сделали и почему?

Исторические удаления — в данных нет даты удаления, поэтому показываем факт истечений
и прогноз, а не вымышленный тренд. Grafana не поднимали: метрики уже отдаются,
визуализация не влияет на решение. ML — не на чем учить. Эти ограничения перечислены
в README и на слайде «Границы».

## 13. Почему OIDC и Keycloak?

Это бонусный пункт кейса и реальное требование B2B-продаж: компания хочет входить
корпоративной учёткой и мгновенно отзывать доступ. Приложение говорит на стандартном
OIDC, Keycloak — только демо-провайдер; в проде подставляется Okta, Entra ID или
Google Workspace через переменные окружения.

## 14. Что дальше?

Накопление снапшотов и калибровка на фактических непродлениях, инкрементальный
пересчёт для больших объёмов, деплой с постоянным диском, Single Logout для SSO.
Порядок — по влиянию на решение маркетолога, а не по красоте технологии.

## 15. Можно ли посмотреть без Docker?

Да: онлайн-стенд <http://193.233.246.179:8000>, вход `admin@example.test` / `admin123`;
SSO — кнопка «Войти через Keycloak», `marketer@example.test` / `marketer123`.
Это тот же образ из репозитория на VPS Aéza. Данные тестовые, HTTPS нет — стенд
только для демонстрации, реальные данные туда не загружаем. Парольный вход и SSO
работают параллельно: если провайдер недоступен, панель всё равно открывается.
