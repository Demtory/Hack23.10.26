# Data Model: 002 — корректность данных и согласованность интерфейса

Это проектирование поверх существующей SQLite; изменения пока не реализованы.
Связи accounts→services→transactions и score_runs→customer_scores сохраняются.

## 1. MoneyCents — строгий входной денежный тип

| Свойство | Правило |
| --- | --- |
| Поля аккаунта | balance, withdrawBalance, totalReplenished, bonusBalance |
| Поля услуги/транзакции | price / amount |
| Единицы | целые евроценты |
| Тип входа | JSON integer → Python int; не bool, string или float |
| Диапазон | 0…9223372036854775807 включительно |
| Недопустимые примеры | −1, true, false, "100", 100.0, 1e2, 100.5, null, отсутствие, overflow |
| Допустимые примеры | 0, 100, amount1001 и amount5000 |

ID сохраняют существующий SQLiteInt; autoProlong остаётся boolean. Финансовый
strict не распространяется на модель, даты или другие поля. Отрицательные и
неверные типы отклоняются с422 до записи. Верхняя граница отдельного входа не
гарантирует представимость всех производных сумм: существующая защита результатов
и атомарный отказ сохраняются. Нулевая цена допустима, но не создаёт достоверный
funds_gap там, где модель считает его неизвестным.

## 2. Исходный снимок и транспорт

Snapshot по-прежнему содержит три обязательных массива и согласованные ссылки.
Сохранённые исходные числа целые, ответ GET/source/snapshot остаётся исходным
форматом, не EUR-отображением. Frontend хранит канонический текст снимка для
скачивания и исходный текст файла для отправки. Разобранные значения не используются
для повторной сериализации больших денежных целых. Object-based API helper
сохраняется, но не может доказать, как число было написано до JSON.parse.

Состояния замены: pending→validated→calculated→committed либо отказ с rollback.
После commit потеря доставки HTTP не означает rollback. Ошибка перечитывания
после успешного PUT не отменяет уже подтверждённую загрузку.

## 3. Поколение признаков и пользовательские настройки

Существующая settings: id1, payload JSON, version INTEGER, updated_at TEXT.
Аддитивное изменение: feature_schema_version INTEGER NOT NULL DEFAULT1.
init_db проверяет PRAGMA table_info и добавляет колонку старой таблице без
пересоздания/удаления. Базовое поколение1 содержит шесть существующих кодов:
expiry_pressure, funds_gap, autorenew_off, status_pressure, payment_history, commitment.

- settings.version — версия пользовательской конфигурации/результатов.
- feature_schema_version — внутреннее поколение набора доступных признаков,
  не передаётся как разрешённый PATCH-параметр и не меняет существующую API-схему настроек.
- Декларация перехода хранит исходное/целевое поколение и добавленные коды.
  Удаление/переименование признаков этой процедурой не поддерживается.
- На новой базе создаются текущие defaults и текущее поколение, version1.
- При переходе старой конфигурации новые отсутствующие коды получают0;
  старые значения и уже сохранённые допустимые новые значения не переопределяются.
- Требуется полная валидность прежних обязательных полей и ключей прежнего поколения.
  Неизвестные коды/версии и потерянные старые ключи вызывают отказ без исправления.

Переход поколения с изменением состояния: BEGIN IMMEDIATE → validate source →
prepare target → validate target → save payload/generation/version+1/timestamp →
recompute → validate serialized response/result → commit. Одна итоговая новая
пользовательская версия при обновлении через несколько поколений за один запуск.
При уже текущем поколении версия не увеличивается. Повторный штатный запуск может
создать новый score_run и updatedAt расчёта, но не новый upgrade.

Колонка добавляется на стадии schema bootstrap; её наличие после отказа данных
не является частично опубликованной конфигурацией. Ни payload, ни его поколение,
ни пользовательский снимок/расчёты не должны фиксироваться частично.

## 4. Расчёт и согласованное представление

score_runs сохраняет id, as_of, created_at, settings_version и summary JSON.
В JSON summary добавляется копия действующих thresholds={medium,high}; значения
фиксируются при recompute вместе с уже существующими агрегатами. Старый latest-run
без контекста заменяется успешным startup/fallback-пересчётом, не смешивается с
текущими settings вне расчёта.

CalculationContext:

| Поле | Источник |
| --- | --- |
| runId | score_runs.id выбранного расчёта |
| settingsVersion | score_runs.settings_version |
| thresholds.medium/high | копия из JSON summary этого же run |

CustomerPage сохраняет items,total,page,pageSize и добавляет topLosses,
summary (глобальные прежние агрегаты), calculation. calculation относится ко всему
ответу, summary внутри page не дублирует его. GET/analytics/summary и summary внутри
ответов PATCH/PUT добавляют calculation рядом с прежними агрегатами.

Один read snapshot фиксирует run_id и JOIN accounts для count/items/top/global summary.
Top использует q/level, expected_loss DESC, account_id ASC, LIMIT5, без OFFSET.
Не меняются денежные формулы, unknown и существующая семантика поиска по email.

Карточка сохраняет DTO: счётчик риска вычисляется по service.level medium/high;
пороги для этих уровней уже применены при том же расчёте, новый запрос настроек
не нужен. Никакой повторной классификации на фронте по40.

## 5. Сессия

Существующие sessions(token_hash,user_id,expires_at,created_at) не меняются.
Выбор credential: непустая cookie sid → иначе Bearer → иначе отсутствие.
Один и тот же resolver используется защищёнными операциями и logout.

- Active→revoked: удаление выбранного token_hash; cookie очищена;200 {ok:true}.
- Revoked/expired/missing→logout: безопасный200, без создания сессии.
- CookieA+BearerB: удаляется только A, B сохраняется.
- Invalid-cookie+valid-Bearer: приоритет cookie сохраняется; защищённый запрос401,
  logout не отзывает B и очищает cookie. Это не новый fallback на другую сессию.
- Frontend очищает токен/пользователя после успешного ответа. При отказе не
  обещает серверный выход; повторный logout остаётся доступен.

## 6. Ошибки и сохранность

Валидация входа:422 без сырых snapshot/credential в ответе. Неожиданный отказ
до фиксации: безопасный500/ошибка startup, rollback и отсутствие нового расчёта.
Повреждённая историческая конфигурация не сбрасывается к defaults/demo.
Изменение source/settings/results и upgrade сравниваются через второе соединение;
успех публикует согласованную версию, отказ — прежнюю.

При фиксированном asOf сравниваются смысловые score/деньги после restart;
служебные runId/updatedAt расчёта могут штатно меняться. На существующем
поколении проверяется неизменность пользовательской settings.version.
