# Research: Корректность данных и согласованность интерфейса

Дата: 2026-10-24. Основание: spec.md после clarify, конституция 1.0.0,
исходники на cf4b092. Это проектные решения, не отчёт о реализованных исправлениях.

## 1. Строгие деньги без конфликта ограничений

**Decision**: отдельный тип MoneyCents — Annotated[int, Field(strict=True, ge=0,
le=2**63-1)] только для balance, withdrawBalance, totalReplenished, bonusBalance,
price, amount. Не наследовать его от нынешнего SQLiteInt и не повторять bounds
в дополнительном Field на каждой позиции. Идентификаторы, boolean-флаги и настройки
модели не переводятся в глобальный strict mode.

**Rationale**: текущая композиция signed64 alias и Field(ge=0) не обеспечивает
объявленную неотрицательность. В предыдущем воспроизведении отрицательные деньги
проходят схему; PUT принимает четыре поля аккаунта и amount, отрицательный price
доходит до расчёта и даёт500. В установленном Pydantic2.14.1 на изолированном
TypeAdapter проверено: 0/100/9223372036854775807 принимаются; −1, overflow,
true/false, строка "100", 100.0, 100.5 и 1e2 отклоняются. Исходники не менялись.
Результирующая JSON Schema имеет minimum0/maximum9223372036854775807/type integer.

Сохранённые денежные колонки при запуске проверяются без коэрции (SQLite typeof
integer и значение>=0); историческая REAL/отрицательная запись вызывает безопасный
отказ без исправления/обнуления. Прежнее происхождение уже сохранённого целого
после коэрции восстановить невозможно, что не меняет явных гарантий spec.

**Alternatives considered**: исправить текущий общий alias — изменит также ID;
глобальный strict — лишнее ужесточение; ручные проверки всех чисел — дублирование
декларативной валидации. Лимит amount1000 убирается по согласованному расширению.

**Contract limitation**: JSON Schema считает 100.0 математически целым. Поэтому
лексическое правило A описывается в description/examples и проверяется реальным
HTTP raw-body, а не только schema-validator. Схема не обещает невозможной проверки
исходного написания числа. Серверный JSON-декодер сохраняет различие int/float.

## 2. Исходный JSON должен дойти до сервера без преобразования

**Decision**: Data.tsx сохраняет исходный file.text(); проверка верхней структуры
через JSON.parse допустима, но PUT отправляет оригинальный текст через отдельный
api.replaceSourceText, без JSON.stringify разобранного объекта. Существующий
объектный api.replaceSource сохраняется для совместимости программных вызовов.
Для скачивания снимка Data использует текст GET/source/snapshot, не повторную
сериализацию числового объекта; разобранный объект нужен только для структуры/счётчиков.

**Rationale**: текущий parse→stringify превращает100.0 в100, обходя правило A,
и округляет большие int64 в JavaScript. Передача текста устраняет обе потери без
JSON-парсера собственной разработки и без новых зависимостей. Сервер остаётся
источником проверки типов и диапазонов. Ответ с денежными отображениями в EUR
сохраняет прежний формат; новая гарантия точности относится к исходным целым.

**Alternatives considered**: regex для поиска дробных литералов ломается на строках
и экранировании; экономический потолок2**53 вместо signed64 меняет согласованный
контракт; сторонний lossless parser не нужен для передачи и скачивания текста.
Успешный PUT не объявляется неуспешным, если последующее перечитывание источника
не удалось: показывается отдельно ошибка обновления отображения.

## 3. Топ, пороги и список из одного расчёта

**Decision**: аддитивно расширить GET/customers полями topLosses, summary
(глобальная сводка), calculation={runId,settingsVersion,thresholds}.
Items/total/page/pageSize и прежние поля записей сохранить.
Один выбранный run и явная короткая read-транзакция обеспечивают snapshot для
count, страницы, топа, JOIN accounts и сводки. _ensure_summary вызывается до
read-транзакции, поскольку fallback может писать. При отсутствии актуального
кэша используется прежняя отдельная write-транзакция пересчёта.

В store.recompute thresholds добавляются в JSON summary score_run вместе с расчётом.
Метаданные выбираются из этой записи, а не из независимо прочитанных текущих settings.
GET/analytics/summary аддитивно получает calculation. PATCH/PUT возвращают этот же
контекст в summary из только что созданного run до commit/отправки ответа.
Для карточки достаточно готовых service.level: medium/high считаются риском;
её DTO не требуется расширять ради повторного получения настроек.

Топ использует тот же WHERE q/level, ORDER BY expected_loss DESC, account_id ASC
и LIMIT5; пагинационный OFFSET и сортировка страницы не применяются. Существующий
q остаётся поиском lower(email) LIKE, включая текущую обработку wildcard; новый
поиск по ID не вводится. Пробелы/обрезка должны одинаково обрабатываться в обоих местах.
Нули/unknown остаются в выбранной совокупности по spec.

**Rationale**: сортировка только items теряет денежного лидера; несколько GET
или SELECT без read snapshot могут смешать новый accounts с прежним кэшем при PUT.
Dashboard публикует целый ответ одним согласованным состоянием, отбрасывая
запоздалые ответы при q/level/sort/page/liveTick. Шкала bar строится по topLosses.
Пороги подписи берутся из calculation. Глобальные карточки помечены как глобальные.

**Alternatives considered**: отдельный endpoint топа требует синхронизации трёх
запросов; выкачать все страницы дороже и подвержено смене данных; BEGIN IMMEDIATE
для обычного чтения блокирует писателей без необходимости. Новая таблица расчётов
не нужна — score_runs уже существует.

Старые JSON summary без thresholds обновляются обычным startup-recompute.
Fallback при чтении старого/неполного кэша должен пересчитать его атомарно,
а не подставлять отдельно текущие пороги к старым результатам. Неизвестные
повреждения данных не маскируются demo/reset.

## 4. Общий выбор текущей сессии и документированный OR

**Decision**: один небольшой resolver для require_user/logout: непустая cookie sid
имеет приоритет; иначе существующий Bearer. Наличие недействительной cookie не
переключает автоматически на другой токен. Для logout не вызывать require_user:
отсутствующая/истёкшая/уже отозванная сессия сохраняет безопасный200 {ok:true}.
Удаляется только выбранный token_hash через существующий delete_session; cookie
очищается. Одна и та же серверная сессия отзывается для обоих способов передачи.

api.ts удаляет auth_token после успешного ответа. App.tsx на ошибке не устанавливает
user=null и не показывает подтверждение выхода, а предлагает повтор. login,
token/accessToken, атрибуты cookie и независимые сессии сохраняются.

APIKeyCookie(auto_error=False) и HTTPBearer(auto_error=False) как зависимости
публикуют альтернативы OpenAPI [cookie,bearer]; runtime сам сохраняет401.
В logout дополнительно разрешена пустая альтернатива {}. На установленном FastAPI
исследовательская проверка в памяти подтвердила два отдельных security-объекта
и возможность добавить {} через openapi_extra без требования аутентификации.
Стандартные зависимости не заменяют правило выбора токена и серверную проверку.

**Alternatives considered**: отозвать оба разных токена противоречит текущей сессии;
поставить require_user на logout ломает идемпотентность; ручная схема без dependency
легко расходится с реально поддерживаемым Bearer.

## 5. Как отличить новый признак от повреждённых настроек

**Decision**: явное поколение схемы признаков feature_schema_version отдельно
от пользовательской settings.version. Сохранить его в одной служебной INTEGER
колонке settings; для старых БД добавить её аддитивно с default1, фиксируя текущие
шесть кодов как поколение1. Существующие сигнатуры публичного get_settings и API
можно сохранить; отдельный внутренний reader получает служебную версию.

В scoring.py — компактные декларации поколений/добавлений без нового реестра классов.
Текущее поколение1 не добавляет реальный новый фактор. Будущий разработчик вместе
с фактором/метаданными/default объявляет переход и новые коды; синтетический
переход1→2 используется только в тестах.

Startup: init_db/schema и bootstrap auth остаются до транзакции данных. Затем в
существующей transaction читаются snapshot/settings/поколение, проверяется исходная
конфигурация по поколению, готовится целевая копия, только объявленным новым отсутствующим
кодам добавляется0, валидируется вся цель, при изменении сохраняются новая схема,
settings.version+1/updated_at, выполняется один recompute и commit. Уже заданные
допустимые значения новых кодов сохраняются. При нескольких переходах за один запуск
публикуется одна итоговая версия. Повторный startup не повторяет upgrade и не увеличивает
settings.version; обычный новый score_run при запуске допустим.

Отсутствующий старый ключ, неизвестный код, нечисловой/неконечный/отрицательный вес,
неподдерживаемое поколение — безопасный отказ без setdefault/reset. Если поколение уже
текущее, пропажа любого его ключа также ошибка. Произвольный ремонт повреждённой базы
не входит в задачу. Чтение GET не запускает скрытые миграционные записи.

**Rationale**: в текущей базе есть только изменяемый номер пользовательской версии,
который не позволяет различить первую установку нового фактора и последующее повреждение.
Явная декларация перехода предотвращает молчаливое восстановление утраченного ключа.
Новая колонка технически необходима для этого различения, не меняет стек/публичный JSON.
Schema bootstrap может оставить только аддитивную пустую колонку после отказа upgrade;
payload/поколение/данные/результаты не меняются частично. DDL не включается в ложное
обещание отката всего init_db/создания администратора.

**Alternatives considered**: setdefault для всех текущих кодов скрывает повреждения;
только фиксированные шесть исходных кодов не обнаружат последующую потерю добавленного
ключа; приватный ключ в публичном payload требует обходить extra=forbid и фильтровать
его во всех ответах. Новая таблица миграций и ORM избыточны.

## 6. Пояснения и проверки без редизайна

**Decision**: Settings.tsx точечно исправляет шесть описаний и формулу:
взвешенная оценка услуги×100, нейтральная обработка неизвестного, status/stale floors,
клиентский max/добавка/cap. Доля веса отличается от фактического вклада.
Текст funds_gap честно описывает сравнение с одной ценой; payment_history — наличие
неоплат, не долю/частоту. Значения и коэффициенты берутся из текущих данных, не
дублируются как несогласованные константы. Формулы scoring не меняются.

Для новой метаописанной фичи неизвестный front-справочник не должен ломать экран:
существующие feature.description/title остаются fallback. Документация описывает
реальные функции вместо несуществующих классов Feature/SourceAdapter.

Backend — pytest/httpx из существующих requirements-dev. Новые проверки в
существующей инфраструктуре плюс отдельные файлы test_customer_views.py,
test_settings_upgrade.py, test_auth_sessions.py, test_openapi_contract.py при
необходимости. Frontend — tsc/Vite build и браузерная интеграционная матрица
на временном APP_DB; новые зависимости не требуются. Не подменять поведенческие
проверки регулярными выражениями по TSX. Использовать имеющиеся browser tools;
при недоступности честно отметить непроверенное, не закрывать соответствующую приёмку.

## 7. Доказательства и ограничения

- Отрицательные деньги, Bearer logout, фильтрованные данные/локальный top,
  ошибка старой конфигурации и расхождение OpenAPI подтверждены прежними
  изолированными воспроизведениями, описанными в spec.md.
- Текст пояснений и parse→stringify подтверждены чтением исходников.
- В текущем планировании проверены строгий числовой тип и OpenAPI OR в памяти.
  Будущие миграции, read-snapshot, исправленный UI и новая OpenAPI не реализованы.
- 99 регрессий 001 прошли при предыдущем аудите; в этой фазе повторно не запускались.
- Нагрузочные пределы, существование плохих данных в рабочей базе и поведение
  новых решений на production не проверены. Нельзя утверждать их готовность.

## Источники технических решений

- [Pydantic2.14.1: strict mode](https://github.com/pydantic/pydantic/blob/v2.14.1/docs/concepts/strict_mode.md)
  — Field(strict=True); проверено также на установленной версии.
- [Pydantic2.14.1: integer constraints](https://github.com/pydantic/pydantic/blob/v2.14.1/docs/api/standard_library_types.md)
  — декларация bounds; причина выбора отдельного типа подтверждена локальным воспроизведением.
- [FastAPI: security reference](https://fastapi.tiangolo.com/reference/security/)
  — optional credential dependencies; конкретный OR проверен в установленном runtime.
- Текущие AGENTS.md, конституция1.0.0 и spec.md; backend/app/{schemas,seed,db,main,
  api,store,security,scoring}.py; frontend/src/{api.ts,App.tsx,types.ts} и pages;
  scripts/export_openapi.py; имеющиеся backend/tests и requirements.

Неопределённости, требующие нового решения пользователя, не остались. Способы
реализации в следующих документах развивают эти решения без расширения на 003.
