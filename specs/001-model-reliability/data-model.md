# Phase 1: данные и переходы состояния

Проектирование для spec.md; существующие SQL-таблицы сохраняются. Этот документ не создаёт миграций.

## Настройки модели

Хранятся в settings: единственная строка id=1, payload JSON, version, updated_at. Payload содержит weights, thresholds, probability, money, statusFloors и существующие остальные параметры. Проверять полную конфигурацию после частичного merge.

| Параметр | Правило |
|---|---|
| weights[*] | Конечные, >=0, хотя бы один >0; сохранить существующие ключи и проверки |
| thresholds | Конечные; 0 < medium < high < 100 |
| probability.midpoint | Любое конечное число, включая10000 |
| probability.steepness | Конечное и >0, включая очень малое положительное |
| probability.floor/ceiling | Конечные; 0 <= floor < ceiling <=1 |
| money.balanceMitigation | Конечное в [0,1] |
| statusFloors[*] | Конечные в [0,100] |

Остальные действующие ограничения сохраняются. Версия и дата изменяются только при успешном применении. Настройки из старой совместимой БД не заменяются defaults. PATCH omission/null верхнего необязательного поля или вложенного необязательного параметра означает «не менять»; null вместо элемента числовой карты — отказ.

## Исходный снимок

SnapshotIn — три явно переданных массива accounts/services/transactions. Явные три пустых массива допустимы; пропуск либо null массива — отказ. Существующие первичные/внешние ключи и правила дат сохраняются.

| Сущность / таблица | Обязательные значения | Связи и исключения |
|---|---|---|
| Account / accounts | id,email,balance,withdrawBalance,totalReplenished,bonusBalance,bonusState | Аккаунт может не иметь услуг; финансовые0 допустимы |
| Service / services | id,name,ownerId,paymentTerm,autoProlong,createdAt,expiresAt,status,price | ownerId → accounts.id; autoProlong=false допустимо |
| Transaction / transactions | id,amount,status,createdAt,type,serviceId; performedAt при performed | serviceId → services.id; при not_performed performedAt отсутствует/null допустимо |

Для обязательных значений отсутствие и null запрещены; проверять наличие, а не truthiness. Деньги остаются целыми евроцентами с прежними доменными границами; значения INTEGER должны помещаться в signed64. Прежние преобразования допустимых типов не ужесточаются глобальным strict mode. При одной ошибке весь снимок отвергается.

Полнота обязательных полей не гарантирует наличие истории/достаточность признаков. При отсутствии транзакций payment_history остаётся неизвестным, а не подтверждённым отсутствием неоплат. Score возможен, если остальных доступных взвешенных признаков достаточно по действующему правилу; иначе сохраняется unknown с причиной недостатка данных. Отсутствие услуг и все услуги deleted сохраняют свои существующие причины unknown. Нельзя подставлять score0. Старое происхождение сохранённых нулей не восстанавливается.

## Результат расчёта

score_runs содержит as_of, created_at, settings_version и summary JSON; customer_scores ссылается на run и аккаунт, содержит значения для сортировки, drivers и detail JSON. Применение настройки или снимка создаёт один согласованный новый результат вместе с изменением. Существующая очистка старых запусков входит в ту же транзакцию.

Связь результатов с settings_version сохраняется. Опубликованный снимок результатов включает детали клиента, список, сводку и метрики. Серия независимых GET вокруг успешного изменения может видеть разные завершённые версии; гарантия не означает заморозку нескольких HTTP-запросов. Ни один завершённый результат не должен опираться на частично записанные данные.

## ExplanationRule — добавление в detail JSON

Точный JSON-контракт: [contracts/api.md](contracts/api.md). Списки `explanationRules` добавляются клиенту и услугам. Старые JSON без списка трактуются как []. drivers сохраняет прежние code/label/contribution/value и единицы вкладов.

| Поле | Смысл |
|---|---|
| code | status_floor, stale_status_floor, customer_bonus, score_cap |
| scope | service либо customer |
| serviceId | ID для service; null для customer |
| label | Понятное основание правила с применённым статусом/минимумом либо числом услуг |
| beforeScore, afterScore, delta | Баллы score, отображаемый переход; delta = round(afterScore − beforeScore, 1) |
| relatedServiceIds | Услуги, участвующие в клиентской добавке; для локального минимума [] |

Правила услуги фиксируют применённые переходы минимумов в порядке расчёта. Не давший эффекта минимум не объявляется прибавкой. Корень клиентского списка содержит только клиентские операции bonus/cap; основания по услугам доступны в services[*].explanationRules и показываются карточкой вместе с ними. Это исключает дублирование баллов разных услуг. Клиентский базовый score остаётся максимумом учитываемых услуг.

При cap разрешён промежуточный beforeScore выше100: например99 →107 (+8), затем107 →100 (−7). Итоговый score по-прежнему <=100; фактическая клиентская прибавка в примере1. Не приписывать клиенту суммарные изменения всех услуг. Расчёт score и денег не меняется. Для объяснения beforeScore и afterScore независимо округляются до одной десятичной позиции тем же round, что используется для score; delta вычисляется как round(afterScore − beforeScore, 1) уже из этих округлённых значений, −0.0 нормализуется в0.0. Применимость правила определяется по фактическим значениям до такого округления: минимум без реального эффекта не создаёт правило. Если минимум действительно сработал, но переход69.96→70 отображается как70.0→70.0, правило сохраняется с delta0.0 и текстом «Применён минимум70; после округления оценка не изменилась», без утверждения о положительной прибавке. UI использует те же округлённые значения; проверки числовых равенств допускают только погрешность представления float1e-9. Случаи без эффекта и с эффектом, скрытым округлением, проверяются отдельно.

## Согласованная операция: переходы

1. Состояние S0 — действующие настройки, данные, результаты.
2. Внешняя операция открывает BEGIN IMMEDIATE; читает актуальную версию, проверяет предлагаемое изменение.
3. Внутри той же транзакции сохраняет предложение и рассчитывает результат; запись/удаление кэша остаются невидимы другим соединениям до commit.
4. Проверяет конечность, представимость, сериализацию и затронутый контракт ответа.
5. Успех → один commit → S1, новый run, затем существующий SSE замечает его.
6. Ошибка на шагах2–4 либо отказ commit до успешной фиксации на шаге5 → rollback → S0, без увеличения version/updatedAt/последнего опубликованного run. После отказа доступны прежние GET и следующая корректная операция.

При startup создание схемы/auth предшествует транзакции данных; defaults/seed/recompute имеют одного владельца. При отсутствии кэша его построение также явно владеет транзакцией. Helpers не начинают вложенные транзакции и не делают commit.

После корректного пустого снимка успешный score_run служит признаком инициализированной БД. Seed разрешён для новой БД без аккаунтов и запусков при прежнем SEED_ON_START; намеренная очистка переживает restart. Идентификаторы AUTOINCREMENT не сбрасывать.

## Совместимость хранения

Новых SQL-таблиц/колонок не нужно. Существующие настройки и записи сохраняются; расширение JSON допускает отсутствие нового поля в старом кэше. Стартовый пересчёт заполнит новые объяснения на совместимых данных. Повреждённые ранее конфигурации не ремонтируются автоматически. Технически непредставимый производный денежный итог не фиксируется; отказ не меняет прежнюю БД.
