# Phase 0: решения исследования

Дата: 2026-10-24. Основание: согласованный spec.md, конституция 1.0.0 и чтение затрагиваемых модулей. Два исследовательских агента независимо проверили SQLite/атомарность и числа/валидацию согласно workflow speckit-plan. Исходники не изменялись; выводы не означают прохождение будущих регрессий.

## 1. Конечные параметры и устойчивый расчёт

**Decision:** использовать имеющийся Pydantic: FiniteFloat либо эквивалентный запрет inf/nan, в том числе внутри карт. Проверять итоговые объединённые настройки. Midpoint — любое конечное число. Сигмоиду вычислять по знаку аргумента так, чтобы exp получал только неположительное значение; сохранить clamp floor/ceiling. Внутреннее ±inf при делении на крайне малую положительную steepness трактовать как насыщение, если входные параметры конечны.

Для обычной конечной суммы весов сохранить текущую арифметику. Только при переполнении суммы перейти к масштабированию весов через максимальный вес. Положительность математической суммы неотрицательных весов проверять наличием хотя бы одного положительного. Финальные score, вероятности, деньги и JSON проверять до сохранения.

**Rationale:** исходный math.exp переполняется на midpoint10000; обычный sum больших конечных весов тоже может переполниться. Это не обосновывает запрет согласованных допустимых параметров.

**Alternatives considered:** ограничить midpoint0–100 — против решения пользователя; scipy/Decimal — ненужные зависимости и риск изменения округления; всегда менять нормирование — больше риск дрейфа штатных результатов.

Источники: [Pydantic 2.14.1: типы](https://github.com/pydantic/pydantic/blob/v2.14.1/docs/api/standard_library_types.md), [Python math](https://docs.python.org/3.12/library/math.html).

## 2. Ошибка валидации тоже должна быть сериализуема

**Decision:** добавить ограниченный обработчик RequestValidationError в main.py: сохранить detail с loc/msg/type, безопасно преобразовывать или исключать несериализуемые input/ctx. Не возвращать сырой снимок и трассировку.

**Rationale:** Pydantic отклоняет NaN/Infinity и число JSON 1e309, но сохраняет исходный неконечный input в errors(). Стандартный JSONResponse запрещает такие числа и способен выдать500 вместо422. Отдельная проба установленного Pydantic подтвердила этот путь; полноценная регрессия API ещё предстоит.

**Alternatives considered:** только FiniteFloat — недостаточно; разрешить NaN в JSON — некорректный контракт; глобальный strict mode — несогласованное расширение ужесточения типов.

Источники: существующие FastAPI/Starlette handlers, [Pydantic serialization](https://github.com/pydantic/pydantic/blob/v2.14.1/docs/concepts/serialization.md).

## 3. Единственный владелец транзакции

**Decision:** явный BEGIN IMMEDIATE в операции до чтения изменяемой версии. Затем merged validation, запись настроек либо снимка, пересчёт, сохранение кэша и проверка возвращаемого JSON. Один commit в конце; при исключении rollback. Убрать собственные commit/rollback из save_settings/replace_snapshot и with conn из recompute. Создание defaults в get_settings не должно неожиданно фиксировать внешнюю транзакцию.

На старте init_db/executescript и bootstrap auth оставить отдельным подготовительным этапом; данные/default settings/seed/recompute выполнять общей транзакцией до готовности приложения. Fallback _ensure_summary также получает явного владельца, когда создаёт результат. Проверить все вызовы изменённых helpers, а не только два endpoint.

**Rationale:** нынешний save_settings сохраняет вредную конфигурацию до расчёта; replace_snapshot аналогично сохраняет исходные таблицы раньше результатов. Вложенный контекст соединения sqlite3 не является вложенной транзакцией и может преждевременно сделать commit.

**Alternatives considered:** обернуть только endpoint в with conn — остаются внутренние commit; компенсирующая обратная запись — опасна при сбое процесса; PostgreSQL/ORM — вне объёма; SAVEPOINT — вложенность здесь не нужна.

Источники: [sqlite3 context manager](https://docs.python.org/3.12/library/sqlite3.html#how-to-use-the-connection-context-manager), [executescript](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Cursor.executescript), [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

## 4. Публикация результата и ошибки

**Decision:** подготовить и проверить ответ до commit, включая JSON с allow_nan=False и соответствие затронутому response DTO. После commit использовать уже проверенную структуру. Не публиковать новый run на отказе. Использовать существующий SSE, читающий через другое соединение; без нового event bus.

**Rationale:** отдельное соединение видит только зафиксированный согласованный результат. Ошибка сериализации после commit иначе нарушит обещание отката при внутренней ошибке. Сбой доставки по сети после commit принципиально не означает отказ изменения.

**Alternatives considered:** уведомление до фиксации — ложное успешное обновление; гарантировать rollback при обрыве сети — невыполнимое обещание. Вводить новую идемпотентность/протокол доставки не требуется.

Источники: [SQLite isolation](https://www.sqlite.org/isolation.html), [FastAPI response_model: validation/filtering](https://fastapi.tiangolo.com/tutorial/response-model/).

## 5. Полный снимок, PATCH и технические диапазоны

**Decision:** убрать значения по умолчанию у обязательных полей снимка, сохранить условное performedAt. Снимок валидируется одной схемой до замены, включая seed. PATCH сохраняет exclude_none: omission/null необязательного поля — без изменения; null внутри числовой карты — ошибка. Прежние проверки дат, enum, ссылок и единиц сохраняются.

Технически непредставимые в signed64 SQLite INTEGER входные идентификаторы/целые денежные значения отклонять с422 до записи; существующие доменные нижние границы сохраняются. Если непредставим производный итог, операция завершается контролируемым отказом до commit. Это предел хранилища, а не новое бизнес-правило суммы. Не вводить новые экономические ограничения или переработку денежных типов; точность JS на огромных суммах — известный отдельный риск.

**Rationale:** пропуск не должен стать достоверным нулём; Pydantic int сам по себе не ограничивает signed64. Принятие большого целого не должно заканчиваться частично записанным состоянием.

**Alternatives considered:** частичный импорт/unknown-поля — пользователь выбрал полный отказ; strict mode — шире согласованного; произвольный потолок денег — нет основания.

Источники: [Pydantic required/nullable](https://github.com/pydantic/pydantic/blob/v2.14.1/docs/migration.md), [SQLite types](https://www.sqlite.org/datatype3.html), [FastAPI partial updates](https://fastapi.tiangolo.com/tutorial/body-updates/) — пример exclude_unset не заменяет согласованную проектную семантику exclude_none.

## 6. Пустой снимок и старые сохранённые данные

**Decision:** существующие таблицы и валидные настройки сохраняются. Новый explanationRules хранить в detail JSON; старый JSON без поля читается как пустой список, при стартовом пересчёте заполняется. Для seed считать базу инициализированной при наличии аккаунтов либо успешного score_run. Принятые три пустых массива обязательно создают пустой успешный run.

**Rationale:** ensure_seed сейчас проверяет только число аккаунтов и после намеренной очистки вернёт demo. Существующий run позволяет избежать новой таблицы-флага. AUTOINCREMENT не обнуляется после DELETE, поэтому успешная замена получает новый наблюдаемый runId. Не менять sqlite_sequence вручную.

**Alternatives considered:** новая таблица metadata — избыточна для данной схемы; всегда засевать пустую БД — против спецификации; восстановить происхождение прежних нулей — невозможно по сохранённым данным.

Источники: текущие db.py/seed.py/store.py, [SQLite AUTOINCREMENT](https://www.sqlite.org/autoinc.html).

## 7. Объяснения и совместимость интерфейса

**Decision:** оставить drivers взвешенными вкладами; отдельный explanationRules описывает фактические минимумы, бонус и cap. Данные фиксировать в точке применения правила. Разделять локальные операции услуги и клиентскую агрегацию; не складывать вклады разных услуг как одну формулу. Карточка рендерит правила независимо от наличия drivers. Summary определяется итоговым уровнем и unknownReason, а не пустотой списка причин.

Добавить ограниченные DTO подробного ответа для документированного контракта. Они обязаны перечислять все текущие поля, включая service.values, даты, деньги и unknownReason: response_model фильтрует неперечисленные поля. Другие API не переводить массово на новые DTO.

**Rationale:** воспроизведение high78 имеет пустые drivers; простое добавление текста без UI не выполнит требование. Смешение +8 баллов и долей weighted contributions исказит графики и семантику.

**Alternatives considered:** добавить фиктивные drivers — нарушает принятое решение; пересчитать модель ради более простого объяснения — вне объёма; редизайн карточки — не требуется.

## 8. Проверки и зависимости

**Decision:** Python pytest/TestClient на временных SQLite, инъекции ошибок в расчёт/позднюю запись/подготовку ответа, отдельное читающее соединение и повторный запуск с тем же файлом. Dev requirements явно объявляют pytest9.1.1 и httpx0.28.1. Существующие frontend build и ручная проверка достаточны для узкого отображения; новый frontend test framework не вводить. Команды и критерии: quickstart.md.

**Rationale:** runtime requirements сейчас не объявляют инструменты существующих тестов. Состояние после отказа и после startup нужно проверять раздельно: startup штатно создаёт новый run.

**Alternatives considered:** проверять только HTTP-код — не доказывает откат; использовать рабочий volume — недопустимо; нагрузочное тестирование — вне объёма.

## Итог исследования

Неизвестные технические решения разрешены. Ограничения доказательств: исходный внешний комплект «Практика» не был прочитан при аудите; используемые raw/demo репозитория нельзя без проверки объявлять его точной копией. Результаты настоящих исправлений должны быть получены на этапе реализации.
