# Контракт изменений API и карточки клиента

Проектирование; root openapi.json пока не изменяется. При реализации экспортировать актуальную схему через scripts/export_openapi.py. Существующие пути, cookie-auth, camelCase, денежные единицы и обязательные операции сохраняются.

## PATCH /api/v1/model/settings

Прежняя частичная структура. Отсутствующее либо null необязательное поле — без изменения. Это относится и к вложенному необязательному параметру. Null вместо числового значения внутри weights/statusFloors не является числом и отклоняется. Неизменённые поля читаются из действующей конфигурации; проверяется итог после merge.

Ограничения чисел — data-model.md. Midpoint10000 принимается. NaN/±Infinity, нечисло, несовместимые пороги, все нулевые/отрицательные веса и steepness0 отклоняются с422. Очень большие конечные веса и малая положительная steepness поддерживаются устойчивой арифметикой.

Успех200: прежние поля настроек, features, version и updatedAt; результат уже пересчитан и зафиксирован общей транзакцией. Неуспех не продвигает версию/дату и не заменяет результаты.

## PUT /api/v1/source/snapshot

Замена целиком; accounts/services/transactions обязательны и не nullable. Перечень обязательных полей и исключение performedAt приведены в [data-model.md](../data-model.md). Существующие проверки ссылок, уникальности, дат и enum сохраняются. Полные raw/demo принимаются. Деньги источника остаются евроцентами, false/0 — действительные значения.

Пропуск/null любого обязательного поля, включая финансовые поля и autoProlong, даёт422 с loc записи/поля. Одна ошибка отвергает весь снимок. Три явно заданных пустых массива успешно очищают данные, создают корректную пустую сводку и остаются пустыми после restart. Сохранить текущую форму успешного ответа PUT; операция считается успешной только после общего commit снимка и результатов.

API- и файловая загрузка используют одинаковую схему. Первичный seed также проверяется целиком до записи.

## Ошибки и согласованность

- 422: ошибки входа/объединённых настроек/связей, включая непредставимые входные INTEGER. Указать поле либо запись; сохранить действующий JSON error envelope detail. Для ошибок Pydantic сохранить loc/msg/type, безопасно исключить/преобразовать невалидный input/ctx. Raw NaN, Infinity и JSON1e309 не должны вызывать ошибку сериализации ответа.
- 500: непредвиденный отказ расчёта, записи или подготовки результата. Вернуть безопасный detail, например «Изменение не применено; сохранено прежнее состояние», без traceback/данных снимка/секретов. До отправки такого ответа транзакция откачена.
- Ошибки авторизации сохраняют текущий контракт.

После отказа исходные таблицы, настройки, version/updatedAt, результаты и метаданные последнего опубликованного run прежние. Сразу после отказа следующая корректная операция и restart успешны. При restart штатный новый пересчёт допустим: сравнивать точные метаданные отказа нужно до него.

Разрыв доставки HTTP после commit не означает откат сохранённого изменения; состояние уточняется GET. Новый протокол идемпотентности не вводится.

## GET /api/v1/customers/{account_id}

Сохранить все текущие поля detail и services, включая drivers/value/contribution, values, confidence, unknownReason, даты, денежные поля и isEstimated. Удалять/переименовывать их нельзя. Новый дополнительный ключ `explanationRules: RuleExplanation[]` в корне и у каждой услуги. Успешный новый ответ содержит массив даже когда он пуст. Чтение старого кэша/старым клиентом совместимо: отсутствующее поле трактуется новым клиентом как [].

| Поле RuleExplanation | Тип и правило |
|---|---|
| code | status_floor / stale_status_floor / customer_bonus / score_cap |
| scope | service / customer |
| serviceId | integer для scope=service, null для customer |
| label | Понятный текст основания и фактически применённого правила |
| beforeScore | Конечное число в баллах score |
| afterScore | Конечное число в баллах score |
| delta | round(afterScore − beforeScore, 1) из округлённых полей, также в баллах |
| relatedServiceIds | integer[], перечисляет участвующие в добавке услуги; иначе [] |

В услуге находятся только её локальные floor-правила. В корне — bonus/cap клиента, без копий правил услуг. Нет эффекта → нет утверждения о прибавке. beforeScore и afterScore округляются до одной десятичной позиции тем же round, что score; delta = round(afterScore − beforeScore, 1) вычисляется из этих округлённых полей, −0.0 нормализуется в0.0. Применимость минимума определяется до округления: если реального эффекта нет, правило не создаётся; если реальный эффект скрыт округлением, правило сохраняется с delta0.0 и поясняет отсутствие изменения отображаемой оценки. Например,69.96→70 передаётся как beforeScore70.0, afterScore70.0, delta0.0 с label «Применён минимум70; после округления оценка не изменилась». UI использует те же значения, не вычисляет прибавку из скрытой точности; тесты допускают погрешность float1e-9. Формулу и округление итогового score/денег это не меняет. Фактический статус/минимум либо число участвующих услуг указывать в label. Последовательность правил сохраняет порядок расчёта. Не переносить delta в drivers.contribution.

Пример клиентской добавки при трёх услугах под риском:

```json
{
  "code": "customer_bonus",
  "scope": "customer",
  "serviceId": null,
  "label": "Три услуги под риском: добавка 8 баллов",
  "beforeScore": 70,
  "afterScore": 78,
  "delta": 8,
  "relatedServiceIds": [101, 102, 103]
}
```

ID в примере синтетические. В реальном контрольном клиенте5 используются ID его услуг. Для каждой услуги, реально поднятой до70 статусом prolong_wait, локальный список содержит status_floor с её фактическим beforeScore и afterScore70. Нельзя суммировать эти локальные изменения как клиентскую прибавку.

При ограничении100 дополнительно показать отдельный cap:99 →107 (+8), затем107 →100 (−7), суммарное повышение клиента1. Промежуточное afterScore бонуса может быть >100; конечный customer.score никогда не превышает100. Не менять эту арифметику ради оформления объяснения.

drivers остаётся прежним массивом взвешенных признаков; при commitment1 контрольный клиент5 вправе иметь drivers=[], score78, levelhigh. Summary и правила должны объяснять этот итог. «Риск ниже порога» запрещён для medium/high; unknown показывает unknownReason. Изменённые пользователем thresholds учитываются при формировании текста.

## Контракт интерфейса

В существующей карточке Customer показать отдельные правила клиента и правила услуг с понятным названием услуги. Рендеринг независим от drivers.length. При отсутствии weighted-причин не скрывать floor/bonus/cap. Не менять графическую шкалу contribution на баллы правил. Старое сообщение «Явных драйверов нет» может относиться только к weighted-признакам, без вывода о низком риске.

Это точечное изменение содержимого; новые страницы, редизайн и компоненты shadcn не нужны.

## Остальные интерфейсы

GET списка/сводки, метрики /metrics, auth, сортировки и получение исходного снимка сохраняют формы и единицы. /api/v1/events сохраняет scores.updated с текущими runId/updatedAt. SSE видит только зафиксированные новые запуски; отказ операции не создаёт успешное обновление. При замене snapshot AUTOINCREMENT не сбрасывается.

Документировать DTO только затронутого detail, без массового изменения остальных ответов. При введении response_model проверить сохранность всех прежних ключей: FastAPI фильтрует неописанные поля. Согласованность проверяется между результатами одной завершённой версии, а не обещанием одной версии для произвольной серии HTTP-запросов во время обновления.
