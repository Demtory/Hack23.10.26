# Проверка после реализации

Руководство использовано при реализации 2026-10-24; результаты и ограничения зафиксированы в docs/STATUS.md. Использовать отдельную копию проекта/рабочую ветку и временную БД; не подключаться к рабочему volume и внешним сервисам.

## Подготовка и автоматические проверки

Из корня репозитория, Python3.12 и Node с npm. Dev-зависимости объявлены в `backend/requirements-dev.txt` согласно plan.md.

```bash
python3.12 -m venv /private/tmp/risk-desk-reliability-venv
source /private/tmp/risk-desk-reliability-venv/bin/activate
python -m pip install -r backend/requirements-dev.txt
PYTHONPATH=backend python -m pytest backend/tests data/raw/test_generate.py -q
npm --prefix frontend ci
npm --prefix frontend run build
```

Если временная папка окружения уже занята другим запуском, выбрать новое имя. Сеть может потребоваться для установки уже выбранных зависимостей; при недоступности отметить установку как непроверенную. Тесты используют tmp_path/отдельный APP_DB, фиксированный as_of и демонстрационные email .test. Ни один тест не должен по умолчанию открывать data/app.db проекта.

Для проверки отказа самого commit внедрить исключение в вызов commit до фактической фиксации для PATCH и PUT. Подтвердить rollback через новое соединение, неизменность version/updatedAt/run и исходных данных/результатов, безопасный ответ без успешного обновления, затем снять отказ, выполнить корректную операцию и restart. Это проверка отказа фиксации, а не потери HTTP после уже успешного commit.

Для атомарности получить снимок всех исходных таблиц, settings payload/version/updated_at, score_runs и customer_scores до операции. После fault injection сравнить через новое независимое соединение. Во время незавершённой операции оно видит прежний согласованный результат; после успеха — новый. В каждом тесте исключения сначала проверить неизменность метаданных, затем снять fault injection, выполнить корректную операцию и повторно открыть приложение с тем же файлом БД. Startup штатно пересчитывает, поэтому новые метаданные после restart допустимы.

Контролировать целые у границ signed64 и непредставимый производный итог: отказ до commit, прежнее состояние сохранено. Не объявлять произвольный новый бизнес-предел суммы.

## Ручная проверка UI и живого обновления

Для изолированного запуска API выбрать незанятый порт, например8017, и новую временную папку БД. Команды из корня, активировано тестовое окружение, frontend уже собран:

```bash
RISK_TEST_DIR=$(mktemp -d /private/tmp/risk-desk-check.XXXXXX)
APP_DB="$RISK_TEST_DIR/app.db" SEED_ON_START=true PYTHONPATH=backend python -m uvicorn app.main:app --host 127.0.0.1 --port 8017
```

Проверить реальное имя app в main.py перед запуском, если оно менялось при реализации. Открыть http://127.0.0.1:8017; использовать существующие демонстрационные данные входа из README. Если окружение переопределяет AS_OF/ADMIN_* или seed, сначала выбрать согласованные тестовые значения, не менять рабочие секреты.

1. В двух вкладках открыть панель и настройки. Сохранить допустимое изменение: панель и деньги обновляются без reload. Убедиться, что получен новый scores.updated либо сработал существующий polling fallback.
2. Получить неполный снимок через синтетический файл: ошибка понятна, прежний список остаётся. Отклонённая операция не даёт нового успешного run/SSE. Не путать периодический polling с событием нового результата.
3. Для клиента5 повторить commitment1 и глазами проверить видимые минимумы/добавку при пустых drivers. Проверить cap, средний/низкий/unknown и изменённые thresholds. По API одного недостаточно, чтобы утверждать исправление UI.
4. Остановить только этот процесс, повторить запуск с тем же APP_DB и проверить настройки/данные. Для пустого снимка отдельно подтвердить, что seed не восстановился. Не удалять working volume и не использовать down -v.
5. Загрузить data/raw/data.json и demo; raw должен дать10accounts/30services/100transactions. Проверить четыре обязательных поля сортировки в обоих направлениях (8 вариантов), пагинацию, login/logout и401 без сессии.
6. На стабильной версии сопоставить числа/суммы панели, деталей, /api/v1/analytics/summary и /metrics. Сохранить экспертную интерпретацию денег и полноты данных.

## OpenAPI и документация

После изменения кода в рабочей копии реализации:

```bash
PYTHONPATH=backend python scripts/export_openapi.py
```

Сверить openapi.json: обязательные поля снимка, nullable optional PATCH, конечные параметры с описанными правилами, новый explanationRules и существующие поля detail. Проверить отсутствие удаления путей/денежных полей/values/drivers. Повторный экспорт должен быть воспроизводим. README должен указывать dev requirements; MODEL — смысл правил, ARCHITECTURE — транзакцию, STATUS — фактически пройденные проверки.

## Критерий завершения

Все FR/SC покрыты матрицей plan.md и подтверждены соответствующими результатами. В отчёте реализации отдельно указать прошедшие, проваленные и пропущенные проверки. Сборка frontend не заменяет проверку видимости правил; старые успешные тесты аудита не доказывают новые исправления. Коммит и push в эту процедуру не входят.
