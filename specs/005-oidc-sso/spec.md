# Feature Specification: Вход через OIDC (SSO)

**Feature Branch**: `main` — доработка ведётся в основной ветке по просьбе команды.

**Created**: 2026-10-24

**Status**: Implemented — согласовано с командой, реализовано и проверено
(`quickstart.md`, `docs/STATUS.md`). OIDC ранее числился отложенным P1 в `docs/STATUS.md`.

**Input**: Нужен вход через SSO (OIDC) в дополнение к парольному. Провайдер — любой,
для демо поднимается Keycloak в compose. Парольный вход сохраняется как fallback,
пользователи создаются автоматически по подтверждённому email из токена.

## Clarifications

### Session 2026-10-24

- Q: Против какого провайдера делаем вход? → A: Универсальный OIDC через `.env`;
  Keycloak в compose профилем `sso` для демонстрации.
- Q: Оставлять ли парольный вход? → A: Да, SSO + пароль как fallback.
- Q: Что делать с неизвестным пользователем? → A: Создавать по email из подтверждённого
  ID token.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Войти через корпоративный SSO (Priority: P1)

Маркетолог открывает панель, нажимает «Войти через Keycloak», проходит вход у провайдера
и возвращается в панель без ввода пароля.

**Why this priority**: это основной сценарий доработки; без него OIDC не имеет смысла.

**Independent Test**: с настроенными `OIDC_*` пройти вход у провайдера и увидеть дашборд
под своим email.

**Acceptance Scenarios**:

1. **Given** OIDC настроен, **When** открыт экран входа, **Then** видна кнопка
   «Войти через {providerName}» и прежняя форма пароля ниже.
2. **Given** нажата кнопка, **When** браузер уходит на провайдера, **Then** запрос
   содержит `response_type=code`, `state`, `nonce`, `code_challenge` (S256).
3. **Given** провайдер вернул код, **When** приложение проверяет токен, **Then** создаётся
   сессия, пользователь попадает на `/#/` и видит свой email в боковой панели.
4. **Given** первый вход нового email, **When** сессия создана, **Then** пользователь
   заведён в `users` без пароля и с `oidc_subject`.

---

### User Story 2 — Ошибки провайдера не ломают вход (Priority: P1)

Если провайдер недоступен, вернул неверный токен или пользователь отменил вход,
маркетолог остаётся на экране входа и может войти по паролю.

**Why this priority**: демо не должно зависеть от доступности внешнего сервиса.

**Independent Test**: отключить провайдера и нажать кнопку SSO — вернуться на экран
входа с сообщением, не потеряв форму.

**Acceptance Scenarios**:

1. **Given** провайдер недоступен, **When** нажата кнопка, **Then** возврат на `/#/login`
   с сообщением «Провайдер входа недоступен» и работающей формой пароля.
2. **Given** истёкший или подделанный токен, **When** обрабатывается callback, **Then**
   сессия не создаётся, пользователь видит понятную ошибку.
3. **Given** state уже использован или отсутствует, **When** обрабатывается callback,
   **Then** вход отклоняется с `state_invalid`.
4. **Given** пользователь отменил вход у провайдера, **When** пришёл `error=access_denied`,
   **Then** показывается «Вход через SSO отменён».

---

### User Story 3 — Прежний вход по паролю не сломан (Priority: P2)

Администратор без настроенного OIDC или при недоступном провайдере входит как раньше.

**Why this priority**: сохранение существующих сценариев — условие конституции.

**Independent Test**: без `OIDC_*` кнопки SSO нет, `admin@example.test` / `admin123`
работает, `/api/v1/auth/me` отвечает.

**Acceptance Scenarios**:

1. **Given** OIDC не настроен, **When** открыт экран входа, **Then** кнопки SSO нет,
   `oidc/start` отвечает 404.
2. **Given** пользователь создан через SSO, **When** он пробует войти по паролю,
   **Then** получает 401.
3. **Given** обычный администратор, **When** он входит по паролю, **Then** поведение
   не изменилось (cookie-сессия, `/auth/me`, выход).

### Edge Cases

- Провайдер вернул `email_verified: false` или пустой email — вход отклоняется.
- `aud` не содержит `client_id`, `azp` не совпадает — вход отклоняется.
- Подпись неверна, `alg` не RS256, неизвестный `kid` (ротация ключей) — отказ;
  для неизвестного `kid` JWKS перечитывается один раз.
- `exp`/`nbf`/`iat` — допуск 30 секунд на расхождение часов.
- Callback без `code`/`state`, повторный state, state старше 10 минут — `state_invalid`.
- Токен-эндпоинт вернул ошибку — `exchange_failed`; сеть недоступна — `provider_unavailable`.
- Приложение в Docker не видит публичный issuer — используется `OIDC_INTERNAL_BASE`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Приложение MUST включать OIDC только при заданных `OIDC_ISSUER` и
  `OIDC_CLIENT_ID`; иначе поведение прежнее.
- **FR-002**: Экран входа MUST показывать кнопку SSO только когда OIDC включён, и MUST
  сохранять парольную форму.
- **FR-003**: Поток MUST быть Authorization Code + PKCE (S256) с одноразовыми `state`
  и `nonce`, хранимыми на сервере, TTL не более 10 минут.
- **FR-004**: Callback MUST проверять подпись ID token по JWKS (RS256), `iss`, `aud`/`azp`,
  `exp`/`iat`/`nbf`, `nonce`, наличие `sub` и подтверждённого email.
- **FR-005**: Первый вход MUST создавать пользователя по email из токена с пустым паролем
  и заполненным `oidc_subject`; парольный вход для такого пользователя MUST быть запрещён.
- **FR-006**: Успешный вход MUST создавать ту же серверную сессию (HttpOnly cookie), что
  и парольный вход, и перенаправлять на `/#/`.
- **FR-007**: Ошибки MUST возвращать пользователя на `/#/login?sso_error=<код>` с понятным
  сообщением и MUST NOT создавать сессию.
- **FR-008**: Парольный вход MUST остаться работоспособным и MUST NOT требовать OIDC.
- **FR-009**: Доработка MUST NOT добавлять runtime-зависимости; HTTP и проверка RSA —
  стандартная библиотека.
- **FR-010**: DEMO MUST поднимать Keycloak оверлеем `docker compose -f compose.yaml -f compose.sso.yaml` с realm,
  клиентом и тестовым пользователем.
- **FR-011**: `openapi.json` MUST содержать новые пути; существующие контракты MUST
  сохраняться.
- **FR-012**: Секреты провайдера MUST NOT попадать в репозиторий; в compose — только
  демонстрационные значения.

### Key Entities

- **OIDC flow** — `state`, `nonce`, `code_verifier`, `redirect_to`, `created_at`; одна
  запись на попытку входа, удаляется при использовании.
- **User** — `email`, `password_hash` (пустой для SSO), `oidc_subject`.
- **Session** — существующая таблица, без изменений.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полный вход через провайдера в браузере доходит до дашборда под email
  из токена.
- **SC-002**: `pytest` → 421 passed (404 + 17 новых), включая проверку настоящей RS256-подписи.
- **SC-003**: Парольный вход и прежние сценарии не сломаны (401 без сессии, `/auth/me`).
- **SC-004**: Ни один отказ провайдера не приводит к 500 и не создаёт сессию.
- **SC-005**: `tsc --noEmit && vite build` и `openapi.json` синхронны с приложением.

## Assumptions

- Доверенный провайдер подтверждает email; email — ключ идентификации. Если email совпал
  с существующим парольным пользователем, аккаунт связывается (`oidc_subject` обновляется).
- Keycloak в compose — только для демонстрации; боевой провайдер настраивается через `.env`.
- Выход из приложения не выполняет Single Logout у провайдера — это следующий шаг.
- Локализация текстов ошибок — русская, как и остальной интерфейс.
