# Requirements Checklist: вход через OIDC (SSO)

**Purpose**: проверить качество требований 005: безопасность входа, полноту ошибок,
совместимость с парольным входом и проверяемость.
**Created**: 2026-10-24
**Feature**: [spec.md](../spec.md)

**Review Ownership**: артефакт проверки требований; `[x]` — критерий качества требований
выполнен, а не факт реализации.

## Безопасность

- [x] CHK001 Поток — Authorization Code + PKCE S256, без implicit (FR-003).
- [x] CHK002 `state` и `nonce` одноразовые, с TTL, хранятся на сервере (FR-003, data-model).
- [x] CHK003 Проверяется подпись, `iss`, `aud`/`azp`, `exp`/`iat`/`nbf`, `nonce`, `sub` (FR-004).
- [x] CHK004 Требуется подтверждённый email; пустой и `email_verified: false` отклоняются (FR-004, edge cases).
- [x] CHK005 Секреты провайдера не попадают в репозиторий; в compose только демо-значения (FR-012).
- [x] CHK006 В URL ошибки нет токенов, email и текстов исключений (data-model, инварианты).

## Совместимость

- [x] CHK007 Парольный вход сохраняется и не требует OIDC (FR-008, US3).
- [x] CHK008 SSO-пользователь не может войти по паролю — проверяемо тестом (FR-005).
- [x] CHK009 Новые маршруты аддитивны, прежние контракты не меняются (FR-011).
- [x] CHK010 Без `OIDC_*` поведение полностью прежнее, `/start` отвечает 404 (FR-001).

## Проверяемость

- [x] CHK011 Каждый код ошибки имеет условие появления и видимый результат (data-model, FR-007).
- [x] CHK012 Подпись проверяется настоящим тестом, а не заглушкой (SC-002).
- [x] CHK013 Полный браузерный вход описан как измеримый сценарий (SC-001).
- [x] CHK014 Демо-провайдер поднимается одной командой и не мешает основному сценарию (FR-010).

## Ограничения зафиксированы

- [x] CHK015 Single Logout, роли и маппинг групп явно вне объёма (Assumptions, plan).
- [x] CHK016 Поддержка только RS256 заявлена честно, ES256/HS256 отклоняются (research R1).
- [x] CHK017 Связывание по email описано как допущение при доверенном провайдере (Assumptions).
