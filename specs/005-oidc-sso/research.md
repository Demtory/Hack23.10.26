# Research: OIDC без новых зависимостей

Дата: 2026-10-24. Контекст: после 004; стек и сессии сохраняются.

## R1. Библиотека или стандартная библиотека

**Решение:** реализовать OIDC-клиент на `urllib` и проверить RS256 на целых числах
(`pow`, `hashlib`, `hmac`).

**Почему:** `requirements.txt` содержит только FastAPI, Uvicorn и Pydantic. `PyJWT`,
`authlib` и `cryptography` не входят в образ; их добавление — новая зависимость ради
двух вызовов. Проверка RS256 по JWK — около 30 строк, покрыта тестами с настоящей подписью.

**Альтернативы:** `authlib` (тянет cryptography и больше кода, чем нужно), `PyJWT` +
`cryptography` (две зависимости), прокси-сервис аутентификации (ломает «один контейнер»).

**Ограничение:** поддерживается только RS256 — алгоритм по умолчанию у Keycloak,
Okta и Google. ES256/HS256 и `alg: none` отклоняются.

## R2. Где хранить state, nonce и PKCE verifier

**Решение:** в SQLite, таблица `oidc_flows`, запись удаляется при первом использовании,
TTL 10 минут.

**Почему:** состояние не зависит от cookie, работает при нескольких воркерах и не
раздувает заголовки. Одноразовость и срок проверяются на сервере.

**Альтернативы:** подписанная cookie (нужен секрет подписи и аккуратная ротация),
in-memory (теряется при рестарте и не масштабируется).

## R3. Публичный и внутренний адрес провайдера

**Решение:** `OIDC_ISSUER` — публичный адрес и ожидаемый `iss`; `OIDC_INTERNAL_BASE` —
адрес для server-to-server вызовов; endpoint-URL из discovery переписываются на внутренний.

**Почему:** в Docker браузер обращается к `http://localhost:8081`, а контейнер приложения —
к `http://keycloak:8080`. Без разделения либо браузер, либо приложение получают
недоступный адрес. Проверка `iss` всегда идёт против публичного значения.

**Альтернативы:** `host.docker.internal` (не работает одинаково на macOS и Linux),
host-network (непереносимо), один общий DNS (вне объёма).

## R4. Идентификация пользователя

**Решение:** ключ — `email` из проверенного ID token; `oidc_subject` хранится для
трассировки; новый email создаёт пользователя с пустым `password_hash`.

**Почему:** у приложения исторически нет ролей и организаций; email уже уникален
в `users`. Пустой хеш не проходит `verify_password`, поэтому SSO-пользователь не может
войти по паролю; при этом существующий `admin@example.test` продолжает работать.
Отдельного флага «только SSO» не требуется.

**Альтернативы:** обязательная предварительная выдача доступов (мешает демо и не
подтверждено требованиями), `sub` как ключ (при смене IdP пользователи потеряются).

## R5. Ошибки и UX

**Решение:** любой отказ → `303 /#/login?sso_error=<код>`, где код — один из
`provider_unavailable`, `state_invalid`, `exchange_failed`, `access_denied`,
`email_unverified`, `token_invalid`, `nonce_mismatch`, `issuer_mismatch`,
`audience_mismatch`, `token_expired`. Текст на русском формирует фронтенд.

**Почему:** пользователь всегда возвращается на экран входа, где работает пароль;
в URL не попадает ничего чувствительного — только код.

## R6. Демо-провайдер

**Решение:** Keycloak 26 отдельным файлом `compose.sso.yaml`, импорт realm
`deploy/keycloak/risk-desk-realm.json`, клиент `risk-desk` с PKCE и тестовый
пользователь `marketer@example.test` / `marketer123`.

**Почему:** без IdP функция не демонстрируется; профиль не запускается по умолчанию,
поэтому жюри по-прежнему делает `docker compose up --build` и входит по паролю.
