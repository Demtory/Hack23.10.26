# Requirements Checklist: понятная причина риска и письмо клиенту

**Purpose**: проверить качество требований 004 до приёмки: полноту, однозначность,
проверяемость и согласованность с конституцией.
**Created**: 2026-10-24
**Feature**: [spec.md](../spec.md)

**Review Ownership**: артефакт проверки требований; `[x]` — критерий качества требований
выполнен, а не факт реализации.

## Полнота и однозначность

- [x] CHK001 Каждая ситуация из запроса имеет требование (FR-003) и критерий проверки (SC-003).
- [x] CHK002 Заголовок ограничен по длине и содержит запрещённые термины явно (FR-001, SC-001).
- [x] CHK003 Поля `summaryDetails` и `emailDraft` описаны контрактом, а не только словами (FR-002, FR-004, contracts/api.md).
- [x] CHK004 Формат сумм и дат задан однозначно, включая тысячи и склонения (FR-005).
- [x] CHK005 Поведение при отсутствии оценки отличается от риска (FR-007, edge cases).

## Проверяемость

- [x] CHK006 Для каждого требования есть наблюдаемая проверка: тест, сборка или браузер (SC-001–SC-005).
- [x] CHK007 Приоритет ситуаций — детерминированный список, а не «по ситуации» (FR-003, data-model.md).
- [x] CHK008 Граница `expiryDays = 0.0` зафиксирована как отдельный случай (edge cases, research R6).
- [x] CHK009 Приёмка воспроизводима по шагам без рабочей БД (quickstart.md).

## Совместимость и ограничения

- [x] CHK010 Прежние поля и пути API сохраняются, изменения аддитивны (FR-011, contracts/api.md).
- [x] CHK011 Старые сохранённые записи остаются читаемыми без миграции (FR-010).
- [x] CHK012 Явно запрещены SMTP, LLM, новые таблицы и runtime-зависимости (FR-012).
- [x] CHK013 Тон письма описан как проверяемое свойство, а не вкусовщина (FR-006, US2).
- [x] CHK014 Реализация не меняет формулы, пороги и денежную модель (plan.md, Constitution Check).
